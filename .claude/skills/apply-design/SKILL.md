# Натянуть макет на тему

Тема — всё в `src/theme/`, контракт — `ThemeModule` (`src/components/site/theme.ts`), правила —
`docs/CLIENT.md` (раздел «Тема клиента»), `docs/DESIGN-GUIDE.md` и `src/theme/CLAUDE.md`.
Код вне `src/theme/` не меняется (кроме генерируемого `docs/BLOCKS.md`). Если для макета нужно
изменение ядра — остановись и опиши, что нужно, вместо обхода в теме.

## 0. Что на входе

- Макет: картинки или PDF от пользователя, ссылка на Figma (через Figma MCP, если подключён).
  Нужны десктоп и телефон; если мобильной версии нет — спроси, прежде чем придумывать.
- Каталог: `docs/BLOCKS.md` (поля и ограничения) и текущая тема в `/_blocks`.
- Если просят часть макета (один блок, шапку) — делай только её, но проверку (шаг 7) проходи всю.

## 1. Разложить макет на блоки

Для каждой страницы макета — стопка блоков. Составь таблицу и покажи пользователю до вёрстки:

| Фрагмент макета | Блок каталога | Вариант | Замечания |
| --------------- | ------------- | ------- | --------- |

- Фрагмент совпадает с блоком по полям, отличается оформлением → вариант (`BLOCK_VARIANTS`).
- Фрагмент другого вида по оформлению, но с теми же полями → тоже вариант, а не новый блок.
- Фрагмент со своими полями, которых нет ни у одного блока → кандидат в свой блок темы.
  Свои блоки согласуй с пользователем: поля, обязательность, ограничения. Если блок пригодится
  другим клиентам, предложи сделать его в ядре.
- Текст макета, которого нет в данных (захардкоженный слоган, телефон в шапке), — найди, откуда
  он придёт: блок, настройки сайта (`docs/BLOCKS.md`, «Настройки сайта»), тексты (`SITE_TEXTS`),
  своя настройка темы (`src/theme/settings.ts`). Тексты в разметке темы — только служебные
  («Все статьи», «Поиск»).
- Отметь, что макет не учитывает по `docs/DESIGN-GUIDE.md`: пустые необязательные поля, длинные
  тексты, число элементов в списках, телефон. Реши разумно и перечисли решения в итоге.

## 2. Токены и шрифты

- Цвета, радиусы, тени — переменные в `src/theme/theme.css` только под `[data-site]` (не на
  `:root` — иначе перекрасится админка). Имена токенов как у shadcn (`--primary`, `--muted`…),
  свои — через `@theme inline`, пример в комментарии файла.
- Шрифты — `next/font` (Google или локальные файлы в `src/theme/fonts/`), переменная на корне
  `SiteLayout`. Нужна кириллица (`subsets: ["latin", "cyrillic"]`). Проверь лицензию шрифта.
- Размеры текста и отступы — утилиты Tailwind в компонентах, одинаковые для всех блоков.

## 3. Оболочка: шапка, подвал, шаблоны

- `site-layout.tsx`, `site-header.tsx`, `site-footer.tsx`. Сохрани: ссылку «К содержимому»,
  `<header>`, `<nav>` с подписью, `<main id="content">`, `<footer>`, поиск (GET-форма на `/search`).
- Сохрани обёртки правки: `EditableText` (название сайта, подвал), `EditableSettings`
  (контакты), `EditablePageTitle`, `EditableBlock`. Без них клиент не сможет править на сайте.
- Логотип и контакты — из `context.settings` (`resolveImage` для логотипа), не из разметки.
- Мобильное меню — без JavaScript, если получится (`<details>`), иначе — маленький клиентский
  компонент в теме.
- Шаблоны страниц (`page-templates.ts` + `templates.tsx`): ширина, крошки, меню раздела. Ключ
  `default` обязателен; новые ключи — только если макет действительно разный по рамке.

## 4. Блоки

- Вид каждого блока — `src/theme/blocks/views.tsx` (`BlockViews`). Данные — `block.data`,
  картинки, ссылки, документы — через `resolveImage`, `resolveLink`, `resolveDocument`
  (`src/components/site/blocks.tsx`): удалённые данные они возвращают как `null`, выводи блок
  без них. Rich text — `RichText` с классом из `src/theme/rich-text.ts`.
- Пропорции картинки — из поля (`docs/BLOCKS.md`, «кадрируется в …»), `next/image` с `fill`
  и `object-cover` в контейнере с этими пропорциями, `sizes` по сетке.
- Варианты — `block.variant` в виде блока и запись в `BLOCK_VARIANTS` (`src/theme/blocks/index.ts`).
- Необязательное пустое поле не выводится вместе со своей обёрткой (отступы, разделители).
- Превью для каталога в редакторе — `src/theme/blocks/previews/<тип>.svg` (схема блока 320×180
  в цветах темы), регистрация в `previews.ts`.

## 5. Свои блоки темы

- `defineBlock` в `src/theme/blocks/index.ts` (`THEME_BLOCKS`): тип латиницей через дефис, не
  совпадает с блоками ядра; поля `field.*`; `example` с реалистичными текстами, картинки и ссылки —
  из `src/lib/blocks/examples.ts`.
- Вид в `views.tsx`, превью, `pnpm blocks:catalog`.
- Схема своего блока после выкатки меняется только совместимо: новые поля необязательные или
  со значением по умолчанию, поля не переименовываются.

## 6. Остальные страницы

`articles.tsx` (список и статья), `search.tsx`, `not-found.tsx` (и пустой сайт) — в том же стиле,
даже если их нет в макете: у каждой `h1`.

## 7. Проверка

1. `pnpm lint && pnpm typecheck && pnpm test` — typecheck ловит блок без вида и шаблон без
   лейаута, `src/lib/blocks/theme.test.ts` — контракт блоков и настроек темы.
2. `pnpm blocks:catalog`, если менялись блоки или варианты.
3. `pnpm build && pnpm test:e2e` — E2E ищут элементы по ролям; если тест упал, исправляй тему,
   а не тест (тесты — ядро).
4. `pnpm theme:screenshots` и посмотри `test-results/screenshots/{desktop,mobile}/`: каждый блок
   (полный пример, варианты, «Только обязательные поля») и страницы. Сравни с макетом: сетка,
   отступы, размеры шрифтов, цвета, поведение на телефоне. Исправь расхождения и сними заново.
5. Проверь клавиатуру и фокус: ссылки и кнопки видны в фокусе, меню открывается с клавиатуры.

## 8. Итог

Коротко для пользователя: какие блоки и варианты использованы, какие свои блоки добавлены,
что решено за дизайнера (пустые состояния, телефон, длинные тексты), что не удалось и почему,
что нужно от ядра. Коммиты — по Conventional Commits с областью `theme`.

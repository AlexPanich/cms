# Сайт для клиента

Один клиент — одна установка и один репозиторий, созданный из этого (ядра). Дизайн клиента — тема
в `src/theme/`, всё остальное приходит из ядра слиянием тега и в репозитории клиента не меняется.
Мультисайта нет: у каждого клиента свой сервер (или свой `docker-compose.prod.yml`), своя база
и свои резервные копии.

Порядок работы:

1. С клиентом обсуждаем дизайн, дизайнер рисует его из блоков каталога — по
   [BLOCKS.md](BLOCKS.md) и [DESIGN-GUIDE.md](DESIGN-GUIDE.md), живой каталог — `/_blocks`
   на любом стенде.
2. Создаём репозиторий клиента (ниже).
3. Натягиваем макет на тему — с Claude, skill `apply-design`.
4. Деплоим, клиент сам наполняет сайт: страницы из блоков, тексты, картинки, настройки сайта.
5. Обновляем ядро по мере выхода версий.

## Создать репозиторий клиента

Нужны: доступ на чтение к ядру и пустой репозиторий клиента (без README и лицензии).

```bash
# Ядро — remote upstream, клиент — origin. Начинаем с последней версии ядра.
git clone --origin upstream git@github.com:AlexPanich/cms.git client-site
cd client-site
git switch -C master v0.3.0            # нужный тег ядра: git tag --sort=-v:refname | head
git remote add origin git@github.com:<организация>/<клиент>-site.git
git remote set-url --push upstream DISABLED   # чтобы случайно не отправить коммиты клиента в ядро
git push -u origin master
```

Затем — первый коммит клиента:

1. `cp docs/client/THEME-CLAUDE.md src/theme/CLAUDE.md` и заполнить: название, домен, где лежит
   макет, шрифты, договорённости. Корневой `CLAUDE.md` подключает этот файл, поэтому правило
   «дизайн только в `src/theme/`» действует в каждой сессии Claude.
2. Закоммитить: `docs(theme): описать сайт клиента`.

Что уже работает в репозитории клиента без настройки:

- CI (`.github/workflows/ci.yml`): проверки, сборка, E2E, `docs/BLOCKS.md`, продакшен-стек
  в Docker.
- release-please не запускается: он ограничен репозиторием ядра. Своих версий и тегов у клиента
  нет, `version` в `package.json` — версия ядра, на которой стоит сайт.
- Демо на Render (`render.yaml`) создаётся, только если подключить репозиторий в дашборде Render.

Теги ядра в `origin` не отправляйте (`git push --tags`): они нужны только локально для слияния.

## Тема клиента

Всё про дизайн — в `src/theme/`, контракт — `ThemeModule` (`src/components/site/theme.ts`):

| Что                                      | Где                                                          |
| ---------------------------------------- | ------------------------------------------------------------ |
| Цвета, радиусы, свои утилиты             | `theme.css` (только под `[data-site]`)                       |
| Шрифты                                   | `next/font` в `site-layout.tsx`, переменная на корне лейаута |
| Шапка, подвал, оболочка страницы         | `site-layout.tsx`, `site-header.tsx`, `site-footer.tsx`      |
| Вид каждого блока                        | `blocks/views.tsx`                                           |
| Варианты оформления, свои блоки          | `blocks/index.ts`                                            |
| Превью блоков в редакторе                | `blocks/previews.ts`, `blocks/previews/*.svg`                |
| Шаблоны страниц                          | `page-templates.ts` (список), `templates.tsx` (лейауты)      |
| Свои настройки сайта                     | `settings.ts`                                                |
| Статьи, поиск, «не найдена», пустой сайт | `articles.tsx`, `search.tsx`, `not-found.tsx`                |
| Правила для Claude в этом репозитории    | `CLAUDE.md`                                                  |

Тема обязана сохранить landmarks (`banner`, `navigation`, `main` с `id="content"`,
`contentinfo`), ссылку «К содержимому», `h1` на каждой странице и обёртки `Editable…` вокруг
полей, которые правятся на сайте: на это опираются доступность, правка на сайте и E2E.

Пример темы, заметно отличной от темы по умолчанию (свой блок, шаблон, настройка), — `e2e/theme/`.

Проверка темы:

```bash
pnpm lint && pnpm typecheck && pnpm test   # typecheck ловит блок без вида и шаблон без лейаута
pnpm build && pnpm test:e2e
pnpm theme:screenshots                     # test-results/screenshots: блоки из /_blocks и страницы
```

## Обновить ядро

Ядро выходит версиями `vX.Y.Z`, что изменилось — в `CHANGELOG.md` ядра. Несовместимые для тем
изменения помечены `!` и описаны в `BREAKING CHANGE`. Обновлять лучше по одной минорной версии.

```bash
git fetch upstream --tags
git switch -c core/v0.4.0
git log --oneline v0.3.0..v0.4.0           # что приходит; CHANGELOG.md — то же человеческим языком
git merge v0.4.0
```

Конфликты:

- **Вне `src/theme/`** их быть не должно — там ничего не меняли. Если есть, берите версию ядра:
  `git checkout --theirs -- <путь>`. Исключение — `docs/BLOCKS.md`: перегенерировать
  (`pnpm blocks:catalog`), в нём есть и блоки темы.
- **В `src/theme/`** — ядро поменяло тему по умолчанию. Оставьте версию клиента
  (`git checkout --ours -- <путь>`) и посмотрите изменение ядра (`git show v0.4.0 -- <путь>`):
  если это новое требование контракта (новый блок, новое поле в пропсах), его нужно повторить
  в теме клиента.

После слияния:

```bash
pnpm install
pnpm blocks:catalog                        # блоки и поля ядра могли измениться
pnpm lint && pnpm typecheck && pnpm test   # ошибки типов в src/theme/ — что нужно добавить в тему
pnpm build && pnpm test:e2e
```

Новый блок ядра теме нужно нарисовать (без вида не соберётся), а дизайнеру — показать
обновлённый `/_blocks`. Миграции БД приходят вместе с ядром и применяются при деплое сами.
Затем PR `chore: обновить ядро до v0.4.0` в репозиторий клиента и деплой.

## Деплой

Продакшен — свой сервер с Docker, как у ядра: раздел «Продакшен» в [README.md](../README.md)
(`docker-compose.prod.yml`, Caddy с HTTPS, резервные копии). Для клиента:

1. DNS домена клиента — на сервер, до первого запуска.
2. На сервере: `git clone` репозитория клиента, `cp .env.production.example .env`, заполнить
   `SITE_DOMAIN`, `POSTGRES_PASSWORD`, `BETTER_AUTH_SECRET` (`openssl rand -base64 32`).
3. `docker compose -f docker-compose.prod.yml up -d --build`.
4. Сразу создать администратора на `https://<домен>/setup` (или из консоли сервера до открытия
   DNS — команда в README) и выдать клиенту учётную запись с ролью «Редактор».
5. Настроить копирование `./backups` наружу.

Обновление сайта (новая тема или новое ядро): на сервере `git pull` и та же команда
`up -d --build` — миграции применятся до старта приложения.

После обновления ядра, добавившего новое право (например, `edit_settings`), проверьте роли
в админке: администратор получает новые права сам, а у «Редактора» они ставятся только при
создании роли.

# План переписывания CMS

Переписываем самописную CMS с Laravel 5.2 / PHP 5.5 (2016 год, `legacy/`) на TypeScript.

## Принятые решения

| Вопрос             | Решение                                                                    |
| ------------------ | -------------------------------------------------------------------------- |
| Подход             | Своя CMS на Next.js (путь A), а не готовый движок вроде Payload            |
| Данные             | База новая, из старой версии ничего не переносим                           |
| URL и дизайн       | Новые: старые адреса сохранять не нужно, вёрстку и тему OneUI не переносим |
| База данных        | PostgreSQL                                                                 |
| Деплой             | Docker (Docker Compose)                                                    |
| Сообщения коммитов | Conventional Commits, описание на русском (подробно в `CLAUDE.md`)         |
| Сайты клиентов     | Отдельная установка и репозиторий на каждого клиента, ядро — из `upstream` |
| Дизайн клиента     | Тема в `src/theme/`, страница собирается из блоков каталога (этап 8)       |

## Стек

- **Next.js** (App Router): SSR публичного сайта и админка в одном приложении.
- **TypeScript** (strict) и **zod** для валидации любого ввода.
- **PostgreSQL** и **Drizzle ORM**.
- **Better Auth** для входа: сессии, регистрация закрыта.
- **shadcn/ui, Tailwind, TanStack Table** для админки, **dnd-kit** для сортировки дерева, меню и галерей.
- **TipTap** как редактор. Он заменяет TinyMCE, CKEditor и Summernote. Виджеты становятся узлами редактора, а не шорткодами.
- **sharp** для миниатюр. Файлы хранятся в томе `storage`, загрузка обычным multipart.
- **Vitest и Playwright** для тестов, **GitHub Actions** для CI.

## Что было в старой CMS

Модули, которые нужно реализовать заново:

- **Страницы**: дерево через `parent_id`, полный путь `full_url` пересчитывается у потомков, у каждой страницы шаблон, SEO-поля, флаг видимости.
- **Меню**: связь меню и страниц с сортировкой, верхнее меню из корневых страниц, подсветка активного пункта.
- **Шаблоны**: страница выбирает лейаут.
- **Тексты**: именованные блоки (`@text(alias)`), которые вставляются в шаблоны.
- **Статьи** с превью-картинкой.
- **Галереи**: загрузка изображений, сортировка, миниатюры, вставка в контент.
- **Документы**: загрузка файлов и список.
- **Пользователи, роли и права**: `view_dashboard`, `edit_pages`, `edit_menus`, `edit_galleries`, `edit_users`, `edit_roles`, `edit_templates`, `edit_documents`, `edit_texts`, `edit_articles`, `edit_from_front`.
- **Редактирование на сайте**: заголовки, контент и тексты правятся прямо на странице.
- **Поиск** по страницам.

## Дыры старого кода, которые нельзя повторить

1. **Выполнение кода через загрузку.** Документы сохранялись в `public/documents` с именем от пользователя и без проверки расширения.
2. **SQL-инъекция в поиске.** Запрос склеивался из строк (`legacy/app/Modules/Search.php`).
3. **Классы по имени из запроса.** `FrontEditController` и `ReplaceWidget` создавали классы по строке из запроса или контента, а `simpleEdit` записывал любые поля модели.
4. **Права не проверялись.** Проверялось только `view_dashboard`, права `edit_*` нигде не использовались.
5. **Удаление через GET** без CSRF-защиты, открытая регистрация, админ из сида с паролем `123456`.
6. **Ошибки в логике:** при удалении страницы её потомки оставались без родителя, при удалении галереи оставались записи изображений, пути пересчитывались без транзакции.

## Этапы

### 1. Каркас ✅

- Next.js 16, TypeScript strict, ESLint, Prettier, Vitest.
- Drizzle, PostgreSQL, мигратор, `/api/health`.
- `Dockerfile` (standalone, приложение не от root) и `docker-compose.yml` (`db`, `migrate`, `app`).
- CI: форматирование, линтер, типы, тесты, миграции, сборка.

### 2. Схема БД ✅

- `pages`: FK `parent_id` (`NULL` для корня, `ON DELETE NO ACTION` — страницу с потомками удалить нельзя), `slug` (CHECK `[a-z0-9-]`), уникальный `path`, `sort`, `menu_title`, `meta_description`, `content` (JSON TipTap; на этапе 8 заменён блоками `blocks`), `template`, `published`, `is_home` (частичный уникальный индекс — главная одна).
- Логика дерева в `src/server/pages/`: при смене slug или родителя пути поддерева пересчитываются в одной транзакции (`starts_with`), защита от циклов, перенос ставит страницу в конец нового уровня, порядок соседей меняется только полным списком.
- `menus` (`key`: `main`, `footer`) и `menu_items`: пункт ссылается либо на страницу, либо на URL (CHECK), сортировка.
- `media`: изображения и документы в одной таблице (`kind`), имя файла в хранилище генерирует сервер. Отдельной таблицы документов нет.
- `galleries` (`key` для вставки в контент) и `gallery_items` с сортировкой.
- `texts` (уникальный `key`) и `articles` (`slug`, превью ссылается на `media`).
- `users` совместима со схемой Better Auth (текстовый `id`); таблицы сессий и аккаунтов добавятся на этапе 3.
- Права — `pgEnum` из констант `src/lib/permissions.ts`, отдельной таблицы нет. Связи `role_permissions` и `user_roles`. Права на шаблоны больше нет (шаблоны в коде), галереи и документы объединены в `edit_media`.
- Сид `pnpm db:seed` идемпотентен: системные роли `admin` (всегда все права) и `editor`, меню `main` и `footer`. В Docker выполняется после миграций.
- Тесты: `slugify`, чистые функции дерева и интеграционные тесты сервиса страниц на настоящем Postgres (каждый тест в откатываемой транзакции).

### 3. Вход и права ✅

- Better Auth 1.7 через Drizzle-адаптер: вход по email и паролю, регистрация отключена (`disableSignUp`), пароль 10–128 символов, сессия 7 дней.
- Таблицы `sessions`, `accounts`, `verifications` рядом с `users`. Экземпляр создаётся лениво (`getAuth()`), чтобы сборка не требовала переменных окружения.
- Вход идёт из браузера через `/api/auth` (клиент `better-auth/react`), поэтому работают встроенные rate limit (3 попытки входа за 10 секунд) и проверка Origin.
- `proxy.ts` быстро отправляет гостей с `/admin` на `/login?next=…`, не обращаясь к БД. Настоящая проверка — `requirePagePermission` на страницах (редирект на вход или 403 через `forbidden()`) и `requirePermission` в server actions (`AuthError`).
- Права читаются из БД на каждый запрос, поэтому изменение ролей действует сразу. `next` после входа проходит через `safeRedirectPath` (защита от open redirect).
- Пользователи создаются `createUserWithPassword` (`src/server/users/service.ts`): пользователь, аккаунт `credential` с хешем из `better-auth/crypto` и роли — одной транзакцией. Первый администратор — `pnpm user:create-admin --email …` или страница `/setup`, открытая, пока пользователей нет.
- Ограничение: страницы стримятся (Partial Prerendering), поэтому 403 и редирект с `/login` для уже вошедшего отдаются в теле ответа со статусом 200. Доступ при этом закрыт; гость получает настоящий 307 от `proxy.ts`.

### 4. Админка ✅

Модули по порядку (✅ — готово):

1. ✅ Основа: shadcn/ui (пресет `base-nova` на Base UI), оболочка с боковым меню по правам, общие компоненты (`src/components/admin/`), единый `runAction` для server actions, формы на react-hook-form + zod.
2. ✅ Пользователи и роли: поиск и пагинация, создание, редактирование, смена пароля (завершает другие сеансы), удаление. Защищены системные роли, права администратора и последний администратор; удалить себя нельзя.
3. ✅ Страницы: дерево, порядок перетаскиванием внутри уровня (мышью и с клавиатуры, объявления для скринридеров на русском), перенос в другую ветку — выбором родителя в форме; форма с SEO-полями, шаблоном и редактором TipTap.
4. ✅ Меню: набор меню задаётся сидом (шаблоны находят меню по ключу), в админке правятся пункты — ссылка на страницу (название берётся из страницы, если своё не задано) или произвольный URL с проверкой протокола (`isSafeLinkUrl`), порядок перетаскиванием. Пункт на удалённую страницу удаляется каскадом.
5. ✅ Тексты: простой текст без оформления (на сайте экранируется, переводы строк сохраняются), ключ в формате slug (CHECK в БД), флаг «показывать на сайте», поиск по названию, ключу и тексту.
6. ✅ Статьи с превью. Дата публикации ставится при первой публикации и дальше не меняется. Превью загружается сразу при выборе файла (`FormImageUpload`, server action с FormData), форма сохраняет только id из `media`.
   Загрузка изображений (`src/server/media/`): до 10 МБ, формат определяется по содержимому (JPEG, PNG, WebP, GIF, AVIF; SVG отклоняется), картинка перекодируется в WebP через sharp с поворотом по EXIF, без метаданных и не больше 2560 px. Файл лежит в `STORAGE_DIR` под случайным ключом и отдаётся обработчиком `/media/[...key]` (ключ проверяется по шаблону, `nosniff`, CSP `sandbox`, кеш `immutable`).
   Загруженная, но не сохранённая в статье картинка остаётся в `media` — её видно в медиатеке с фильтром «Неиспользуемые».
7. ✅ Галереи: название и ключ для вставки (slug, CHECK в БД). Несколько файлов за раз — выбором или перетаскиванием в зону загрузки; клиент отправляет их по одному (лимит размера server action), сервер загружает в галерею под блокировкой и ставит в конец. Порядок перетаскиванием в сетке (dnd-kit, как в меню), описание картинки (`alt`) в диалоге.
   Убранная из галереи картинка и картинки удалённой галереи удаляются вместе с файлом, если больше нигде не используются (галереи, превью статей); файлы удаляются после фиксации транзакции.
   Медиатека `/admin/media`: все изображения, поиск по имени файла, где используется, фильтр «Неиспользуемые», удаление (из галерей пропадёт, у статей уберётся превью).
   Вставка галереи в контент — на этапе 5 (реестр виджетов).
8. ✅ Документы (`src/server/documents/`, записи `media` с `kind = document`): название и файл до 20 МБ. Белый список расширений — PDF, Word, Excel, PowerPoint, OpenDocument, RTF, TXT, CSV, ZIP (`DOCUMENT_EXTENSIONS` в `src/lib/media.ts`), содержимое сверяется с сигнатурой формата: `shell.php.pdf` с PHP внутри не пройдёт. Файл хранится как есть в `STORAGE_DIR/documents` под случайным именем, MIME — из белого списка, а не от браузера.
   Обработчик `/media/documents/…` находит запись по ключу и отдаёт файл только как вложение (`Content-Disposition: attachment` с исходным именем в UTF-8), с `nosniff` и CSP `sandbox`. Удаление документа удаляет и файл.

Общее для всех модулей: таблицы с пагинацией и поиском, формы на zod, уведомления, подтверждение удаления.

Отступления от исходного плана:

- Таблицы рендерятся на сервере, пагинация и поиск — через параметры URL (`?q=&page=`). TanStack Table не понадобился: списки небольшие, а серверные таблицы работают без JavaScript.
- У документов нет флага «показывать на сайте» (был `is_show` в старой CMS): скрытый документ всё равно скачивался бы по прямой ссылке. Ненужный документ удаляют. Заменить файл у существующего документа нельзя — адрес файла меняется, поэтому загружается новый документ.
- Миниатюры не хранятся отдельными файлами: их на лету делает `next/image` (тоже на sharp) и кеширует сам. На диске лежит только перекодированный оригинал.
- Playwright подключён уже на этапе 4, а не на этапе 7: формы админки целиком на клиентском JavaScript, и без E2E их не проверить.

### 5. Публичный сайт ✅

- Маршруты в группе `src/app/(site)/`: `[[...slug]]` ищет опубликованную страницу по `path` (сегменты проверяются по формату slug до запроса), главная — страница с `is_home` на `/`, по своему пути она перенаправляет на `/`. Статьи — `/articles` и `/articles/[slug]`, поиск — `/search`.
- Корневые адреса разделов (`admin`, `api`, `articles`, `login`, `media`, `search`) нельзя занять страницей: `RESERVED_ROOT_SLUGS` в `src/lib/slug.ts`, проверка в схеме страницы.
- Шаблоны — React-лейауты из реестра `templates` темы (`src/theme/templates.tsx`, до этапа 8 — `src/app/(site)/_templates/`) (`Record<PageTemplate, …>`, без лейаута для ключа не соберётся): «Стандартный» — текст, хлебные крошки и меню раздела сбоку, «Широкий» — без бокового меню.
- Шапка с главным меню (`main`, активный пункт подсвечивается и на вложенных страницах) и поиском, подвал с меню `footer`. Название сайта, описание и текст подвала — тексты `site-name`, `site-description`, `footer` (`SITE_TEXTS` в `src/lib/site.ts`), их создаёт сид. Пункты на неопубликованные страницы и скрытые тексты не выводятся.
- Контент TipTap выводится на сервере компонентом `RichText` (`src/components/site/rich-text.tsx`) по явному реестру узлов, без `dangerouslySetInnerHTML`: неизвестные узлы пропускаются, ссылки проверяются `isSafeLinkUrl`, текст экранируется.
- Галерея в тексте — узел редактора `gallery` с ключом галереи (кнопка «Вставить галерею» в редакторе страниц и статей). Данные виджетов документа загружаются заранее одним запросом (`loadContentContext`).
- SEO: метаданные собирает `siteMetadata` (`(site)/_lib/metadata.ts`) — заголовок «Страница — Сайт», описание (если не задано — начало текста, `richTextExcerpt`), canonical, Open Graph и карточка для соцсетей. JSON-LD: `WebSite` с поиском на главной, `BreadcrumbList` на страницах и статьях, `Article` у статей. `sitemap.xml` (опубликованные страницы и статьи) и `robots.txt` (закрыты `/admin`, `/login`, `/api`). Адрес сайта — `BETTER_AUTH_URL`.
- Публичная часть рендерится без стриминга: в лейауте сайта `instant = false` и `generateViewport` с `connection()`, внутри — ни одного `<Suspense>`. Поэтому метаданные в `<head>` для всех клиентов и ботов, а текст — сразу в HTML, а не в скрытом блоке, который вставляет скрипт (так было при стриминге, и Яндекс мог не увидеть текст).
- Статусы ответа ставит `proxy` до рендера: с Cache Components рендер страницы не может вернуть ничего, кроме 200, даже при `notFound()`. Proxy проверяет адрес в БД (`resolveSiteRoute`): нет опубликованной страницы или статьи — 404 (тело — та же страница «не найдена» в оформлении сайта, её proxy получает внутренним запросом к самому приложению), путь главной — 308 на `/`. Навигацию на клиенте proxy не трогает — её «не найдена» рисует сама страница.
- Поиск: колонка `search_vector` у страниц и статей — generated column с GIN-индексом, Postgres сам считает её из заголовка (вес A), описания (B) и значений полей `text` документа TipTap (C), без адресов ссылок и типов узлов. Запрос — `websearch_to_tsquery('russian', $1)` параметром, сортировка по `ts_rank`, фрагменты `ts_headline` с маркерами, которые на странице превращаются в `<mark>` (фрагмент выводится как текст). Страница поиска закрыта от индексации.

- Кеш: данные публичных страниц читаются через `"use cache"` (`src/server/site/cached.ts`) с тегом на каждый тип данных — страницы, меню, тексты, статьи, галереи — и профилем `hours` (сам обновляется раз в час на случай правок в обход админки). `runAction` после успешного действия сбрасывает теги, которые может изменить его право (`SITE_CACHE_TAGS_BY_PERMISSION`, `updateTag` — редактор сразу видит правку). Чтения по пути и slug идут только для адресов из закешированного индекса опубликованного, поэтому запросы на несуществующие адреса не засоряют кеш. Поиск не кешируется. Полный сброс — `POST /api/site-cache` (право `view_admin`): для правок прямо в БД и E2E.

Ограничения:

- Proxy делает один запрос в БД на каждый показ публичной страницы (`"use cache"` в proxy не работает).
- Кеш хранится в памяти процесса. Для нескольких экземпляров приложения нужен общий `cacheHandlers` (например, Redis) — иначе правка сбросит кеш только в одном из них.

### 6. Редактирование на сайте ✅

- Белый список полей — схема `frontEditInputSchema` (`src/server/front-edit/schema.ts`): `page.title`, `page.content` (на этапе 8 — `page.block`) и `text.body`, значения проверяются теми же правилами, что в админке. Других полей в схеме нет, поэтому адрес, публикацию или шаблон так не поменять (в старой CMS `simpleEdit` записывал любые поля модели).
- Править можно только то, что видно на сайте: опубликованную страницу (по id) и показываемый текст (по ключу). Черновики и скрытые тексты — только из админки.
- Сохранение — server action `saveFrontEdit` (`src/app/(site)/actions.ts`) через `runAction("edit_from_front", …)`: проверка права, а после сохранения сброс тегов кеша страниц и текстов — правка сразу видна, перезагрузка не нужна.
- На сайте правятся заголовок и текст страницы (TipTap, тот же редактор и вставка галерей, что в админке), название сайта в шапке и текст в подвале. Серверные обёртки `Editable…` (`src/components/site/editable.tsx`) проверяют право (`getFrontEditor`: гость без cookie сессии — без запроса в БД) и только тогда выводят клиентский редактор.
- Внизу справа — панель «Править на сайте» (режим правки сохраняется при переходах) и ссылка в админку, если есть `view_admin`. В режиме правки блоки обведены и у каждого кнопка «Изменить»; одновременно открыт один редактор, Escape — отмена.
- Код правки грузится отдельным чанком через `next/dynamic` (`front-edit-lazy.tsx`), только когда отрендерен. Условного рендера мало: Next подключает скриптом к каждой странице все клиентские модули, импортированные в сегменте, и без этого гости получали бы TipTap (~900 КБ).

### 7. Тесты и деплой ✅

- E2E на Playwright дописывались вместе с модулями (этапы 4–6). Сквозной сценарий «страница из админки → на сайте» — в `e2e/pages.spec.ts`: опубликованная страница видна по новому адресу после смены slug, старый адрес и черновик — 404, после публикации черновик появляется на сайте. Загрузка в галерею и вставка в текст — `e2e/galleries.spec.ts` и `e2e/site.spec.ts`.
- Продакшен — один сервер, `docker-compose.prod.yml` (проект `cms-prod`, чтобы не пересекаться с dev-стеком): `db`, `migrate`, `app`, `caddy`, `backup`. Секреты — переменные в `.env` (образец `.env.production.example`), обязательные помечены `:?` и без них compose не запустится. Наружу открыт только Caddy (80, 443), у всех сервисов `restart: unless-stopped` и ограничение размера логов.
- Caddy (`docker/Caddyfile`): HTTPS от Let's Encrypt для `SITE_DOMAIN`, сжатие, лимит тела 21 МБ (как `serverActions.bodySizeLimit`), HSTS. `BETTER_AUTH_URL` собирается как `https://SITE_DOMAIN`.
- IP клиента для rate limit Better Auth — `X-Forwarded-For` с одним адресом (`advanced.ipAddress` в `src/server/auth/auth.ts`). Caddy ставит его сам и отбрасывает присланный клиентом, Next ставит заголовок, только если его нет. Проверено: через Caddy подделка заголовка не обходит лимит (четвёртая попытка входа — 429), напрямую в приложение — обходит, поэтому порт приложения наружу не открывается.
- Резервные копии (`docker/backup.sh` в сервисе `backup` на образе `postgres:17-alpine`, той же версии, что сервер): `pg_dump` в custom-формате и tar-архив `storage` при запуске и раз в `BACKUP_INTERVAL_HOURS`, хранение `BACKUP_KEEP_DAYS` дней, недописанная копия не выглядит готовой (`.tmp` до конца). Восстановление — `backup.sh restore <метка>`: `pg_restore --clean` в одной транзакции и замена файлов с владельцем приложения. Каталог копий — на сервере, вынос наружу — средствами сервера.
- Демо-стенд на Render (бесплатный план, `render.yaml`): web service из `docker/render.Dockerfile` (миграции и сид при старте — pre-deploy команды на бесплатном плане нет) и Render Postgres. Файлы эфемерные, база удаляется через 30 дней, лимит входа общий для всех: прокси Render присылает `X-Forwarded-For` списком. Деплой после зелёного CI в `master`. MCP Render для Claude Code — `.mcp.json`.
- Релизы — release-please по Conventional Commits: release-PR, `CHANGELOG.md`, теги `vX.Y.Z`.
- CI: job `docker` поднимает продакшен-стек целиком (Caddy на `localhost` с локальным сертификатом), проверяет `/api/health` через HTTPS и наличие первой резервной копии; `shellcheck` для `backup.sh`.

Отложено:

- Несколько экземпляров приложения: общий обработчик кеша (`cacheHandlers`, например на Redis), см. этап 5, и хранилище rate limit в БД. Пока экземпляр один, кеш и счётчики в памяти работают правильно.
- Запрос в БД из proxy на каждый показ страницы (см. ограничения этапа 5). Сначала измерить под нагрузкой: это один запрос по уникальному индексу. Если станет узким местом, то по порядку:
  1. Индекс опубликованных адресов в памяти proxy с коротким сроком жизни (около 30 с). Адрес из индекса — без БД, промах — проверка в БД, поэтому новая страница доступна сразу. Отстаёт только снятие с публикации: до срока жизни 200 вместо 404, страница при этом рисует «не найдена» с `noindex`. `updateTag` этот индекс не сбрасывает — proxy не видит кеш `"use cache"`.
  2. Для нескольких экземпляров — точный сброс индекса через `LISTEN/NOTIFY`: триггер на `pages` и `articles`, у каждого экземпляра одно соединение с `LISTEN` (с переподключением). Срабатывает и на правки в обход админки.
  3. При серьёзной нагрузке — кеш ответов гостям перед приложением (Nginx или CDN) вместе со статусом. Ответы с cookie сессии не кешировать, иначе пропадёт панель правки на сайте; сброс после правок или микрокеш на 5–10 с.
  4. Убрать проверку из proxy, если Next научится ставить статус ответа при рендере с Cache Components.
- После запуска удалить `legacy/` отдельным коммитом.

### 8. Темы и блоки: дизайн под клиента

Как работаем: с клиентом обсуждаем дизайн, дизайнер рисует его из блоков каталога, тема натягивается на CMS (с Claude) в отдельном репозитории клиента. Дальше клиент сам правит тексты и картинки, добавляет и удаляет страницы и собирает их из блоков.

Решения:

- **Один клиент — одна установка и один репозиторий**, созданный из этого. Ядро приходит слиянием тега из `upstream` (`git merge upstream/vX.Y.Z`). Мультисайт (несколько доменов в одной установке, `site_id` в таблицах) не делаем: кеш и rate limit в памяти, база и деплой на один сайт. Ядро не выносится в npm-пакет: маршруты App Router должны лежать в `src/app` самого приложения.
- **Граница ядро/тема.** Всё, что относится к дизайну клиента, лежит в `src/theme/` и подключается через алиас `@/theme`. Ядро (`src/app/(site)`) загружает данные, ставит метаданные, JSON-LD и обёртки правки на сайте, а разметку берёт из темы. В репозитории клиента код вне `src/theme/` не меняется. Если теме чего-то не хватает, это доработка ядра здесь, и к клиенту она приходит с обновлением. Тема по умолчанию — нынешний дизайн, она же образец.
- **Страница — вертикальный список блоков.** Шапка и подвал общие и принадлежат теме, контент между ними состоит из блоков. Блок — это тип из каталога и данные, проверенные его схемой. Rich text — тоже блок (`text`), поэтому обычная текстовая страница — один такой блок. У статей остаётся rich text без блоков.
- **Тип блока описывается один раз** через небольшой DSL полей (`defineBlock`, `field.text()`, `field.richText()`, `field.image()`, `field.link()`, `field.list(...)`, `field.select(...)`, `field.boolean()`). Из описания выводятся zod-схема (сервер, форма, правка на сайте), форма в админке, текст для поиска, ссылки на `media` для подсчёта использования, пример данных для каталога и описание для дизайнера. Ограничения (длина, число элементов, пропорции картинки) задаются в поле и действуют везде одинаково.
- **Описание блока в ядре, вид в теме.** Ядро держит базовый каталог блоков, тема обязана нарисовать каждый (`Record<BlockType, …>`, без компонента не соберётся). Тема может объявить у блока варианты оформления (`variant`: «картинка справа», «на тёмном фоне») и добавить свой тип блока в `src/theme/blocks/`. Свой тип нужен, если в каталоге нет ничего похожего. Если блок пригодится другим клиентам, его переносят в ядро.
- **Схемы блоков меняются только совместимо**: новые поля необязательные или со значением по умолчанию, поля не переименовываются. Блок, который не прошёл схему или тип которого неизвестен, на сайте не выводится (как неизвестный узел rich text), а в админке помечается «нужно исправить». Несовместимое изменение — только с миграцией данных.
- **Настройки сайта** (логотип, телефон, адрес, соцсети) тема описывает теми же полями (`themeSettings`). Хранятся одной записью `jsonb`, правятся в админке («Настройки сайта») и на сайте. `SITE_TEXTS` остаются для названия, описания и подвала.
- **Каталог для дизайнера генерируется из кода**, а не ведётся руками:
  - `pnpm blocks:catalog` пишет `docs/BLOCKS.md`: блоки, поля с ограничениями, варианты. CI проверяет, что файл не устарел;
  - живой каталог `/_blocks` на сайте рисует каждый блок и вариант на примерах данных в стилях темы. Доступен только с `view_admin`, `noindex`. По нему дизайнер видит, что уже есть, а Claude проверяет натянутую тему;
  - правила для дизайнера — `docs/DESIGN-GUIDE.md`: страница — стопка блоков, у каждого блока мобильная версия, длина текстов переменная, у необязательных полей есть пустое состояние, картинки с заданными пропорциями. Новый вид блока лучше нарисовать как вариант существующего, новый тип — отдельно согласовать.

Доступ — `view_admin`, `noindex`, закрыт в `robots.txt`; адрес пропускает `classifySitePath` (`BLOCK_CATALOG_PATH`). `pnpm blocks:catalog` пишет `docs/BLOCKS.md` (`renderBlocksDoc`: блоки, поля с ограничениями, варианты, настройки сайта; через prettier), `--check` — шаг CI. Правила для дизайнера — `docs/DESIGN-GUIDE.md`. E2E `e2e/catalog.spec.ts`.
10. ✅ Процесс для клиента. `docs/CLIENT.md`: создать репозиторий (`git clone --origin upstream`, ветка от тега ядра, запрет push в `upstream`), тема клиента (где что лежит, обязательная разметка), обновить ядро (`git merge vX.Y.Z`; конфликты вне `src/theme/` — версия ядра, в `src/theme/` — версия клиента и сверка с изменением ядра; `docs/BLOCKS.md` перегенерировать), деплой. Правила клиента для Claude — `src/theme/CLAUDE.md`: корневой `CLAUDE.md` подключает его (`@src/theme/CLAUDE.md`), в ядре там описание темы-образца, в репозиторий клиента копируется шаблон `docs/client/THEME-CLAUDE.md` («дизайн только в `src/theme/`», чего не хватает — доработка ядра). Skill `.claude/skills/apply-design`: разложить макет на блоки и варианты (таблица соответствия до вёрстки), токены и шрифты, оболочка с обязательными landmarks и обёртками правки, виды блоков, свои блоки с `example`, остальные страницы, проверка. Для проверки — `pnpm theme:screenshots` (`e2e/screenshots.spec.ts`, запускается только с `SCREENSHOTS_DIR`): каждый блок из `/_blocks` и основные страницы на 1280 и 390 px. release-please запускается только в репозитории ядра: у клиента нет своих версий, `version` в `package.json` — версия ядра.
11. ✅ Проверка контракта: вторая тема `e2e/theme/` — тёмная, с другим шрифтом и другой разметкой всех блоков, свой блок `quote`, свои варианты, шаблон `landing` и нет `wide`, своя настройка `slogan`, превью только у своего блока. В обычной сборке её нет (исключена из `tsconfig.json` и из сканирования Tailwind). `pnpm theme:contract` (`scripts/theme-contract.sh`) подставляет её на место `src/theme/`, как тема клиента, и гоняет typecheck, lint, unit-тесты, сборку и `e2e/theme-contract.spec.ts`; в CI — задача `theme-contract`, локально — в копии репозитория на порту 3100. `e2e/theme-contract.spec.ts` проверяет только обязательное для темы (landmarks, ссылка «К содержимому», один `h1`, поиск, обёртки правки, пропавший шаблон, 404, каталог с блоками темы) и проходит на обеих темах. Прогон нашёл два unit-теста, завязанных на тему по умолчанию (точный набор настроек, вариант «Картинка справа»), — теперь они от темы не зависят.

Отложено:

- Несколько клиентов на одном сервере: общий Caddy на 80/443 и проекты `app + db + backup` за ним. Сейчас у каждого `docker-compose.prod.yml` свой Caddy.
- Предпросмотр черновика страницы перед публикацией. Для сборки страниц из блоков он понадобится скоро.
- Макет из Figma через Figma MCP, если дизайнер работает в Figma.

## Оценка

Около 4–5 недель работы одного разработчика. Переноса данных и сохранения URL нет, поэтому работы меньше, чем в первой оценке.
